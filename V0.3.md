# MomBoard v0.3 — "From advisor to collaborator"

*Release definition. v0.1 (T01–T23) stores and tags conversations. v0.2 (T24–T45) made the repository talk back — it preps you, nags you, answers you with receipts, and trains you. v0.3 makes the corpus **feed other tools**: evidence and synthesis become an MCP-exposed source that external agents build on.*

## Theme

v0.2 answered "what should *I* do next?" v0.3 answers "what can *other tools* do with this?" The repository stops being a destination and becomes a **grounded source of truth that agents compose with** — exposing insights, summaries, and themes over MCP so a design or planning agent (e.g. Claude's artifacts/design surface) can draft epics and prototypes from real, cited customer evidence instead of from a blank page.

The bet: MomBoard should not try to *be* a design or planning tool — it should be the **evidence layer** those tools stand on. Everything a human reviewer would need to trust an AI-drafted epic (the quote, the conversation, the hypothesis it supports) is already in the repository; v0.3 makes it reachable by the agent doing the drafting.

## Scope

**Corpus-as-MCP-source** — the repository talks to *other tools*:
| Task | Feature | Spec |
|---|---|---|
| T26 (reframed) | **Insights & summaries over MCP** — extend the v0.2 MCP server (T25) with tools that expose syntheses, themes, segment lenses, and per-conversation summaries as structured, citation-backed payloads. The corpus becomes queryable by any MCP client. | needs task file |
| T46 | **Epic / prototype drafter** — an agent workflow (over the MCP tools above) that, when a theme crosses a strength/evidence threshold, drafts an epic *and* a prototype brief into a human review queue. Every claim cites highlight IDs; nothing is auto-promoted. Prototyping itself happens in the external design surface — MomBoard supplies the grounded brief, not the mockup. | needs task file |

**Extensibility** — make the repository fit any team:
| Task | Feature | Spec |
|---|---|---|
| T47 | **Custom taxonomy, first-class** — teams define their own tags (key, emoji, description, signal strength) through the UI; new tags flow into the tagger prompt automatically and apply on reprocess. Generic capability — no team-specific labels shipped. | partial (API exists) — needs UX + docs |

**Explicitly OUT of v0.3** (→ later): T37 Zoom (no demand yet); T33 model eval harness (an internal dev utility, not a user-facing feature — users already pick models via the pluggable OpenAI/Bedrock backends and per-agent model selection); anything team-specific baked into the public repo. The MCP-first direction deliberately replaces the original T26 ("MomBoard internally generates concept mockups") — the repository exposes evidence; external design tools do the mockups.

## Build order

```
1. T26 insights/summaries MCP tools   (keystone — everything else consumes these)
2. T47 custom taxonomy                (independent; sharpens the signal the tools expose)
3. T46 epic/prototype drafter          (the payoff; needs T26's tools + a review queue)
```

Rationale: 1 exposes the corpus so anything can build on it; 2 lets teams shape the vocabulary those insights are organized around; 3 is the first real consumer of the MCP surface and proves the "grounded drafting" thesis.

## Design principles (carried from v0.2)

- **Citation or silence.** Every insight the MCP exposes, and every epic/prototype brief drafted from it, carries the highlight IDs it rests on. No ungrounded claims cross the MCP boundary.
- **Human-in-the-loop.** The drafter proposes into a review queue; a human promotes. Nothing an agent writes is auto-filed as a real epic.
- **MomBoard stays in its lane.** It is the evidence layer. Design, prototyping, and ticket systems are external; MomBoard feeds them, it does not become them.
- **No required-click regression.** The core Library/Conversation flow gains nothing mandatory. New surfaces are opt-in.

## Definition of done (release gate)

- All tasks green under `tasks/README.md` conventions (LLM faked in tests, both DB dialects in CI, Pydantic twins for every schema).
- An MCP client can: list syntheses, fetch a theme with its evidence, and request a drafted epic brief for a strong theme — all returning verbatim-cited payloads.
- Custom tags can be created in the UI, appear in the tagger prompt, and apply to reprocessed conversations (tested end to end).

## Risks / watch-list

- **MCP payload trust.** Insights exposed over MCP must degrade honestly — empty themes and gap-answers, never padding — because a downstream agent will treat them as ground truth. Tested.
- **Drafter over-reach.** The epic/prototype drafter must never promote its own output or invent evidence; the review queue and citation validation are the guardrails, not optional polish.
- **Taxonomy sprawl.** Custom tags that overlap dilute the tagger's signal. The UX should encourage a small, sharp set and surface near-duplicate descriptions.
- **Scaling note (not a v0.3 feature).** The MCP/drafter direction invites larger corpora. The schema is already PostgreSQL-compatible; moving off single-file SQLite is the enabling step before high-volume, continuous ingestion — planned as infrastructure, not shipped as a user feature here.
